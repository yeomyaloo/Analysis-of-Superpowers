# 6. 쓸 때 vs 안 쓸 때 — 성능 차이

![superpowers 사용/미사용 비교](../images/performance.svg)

## 결론부터

| 질문 | 답 | 근거 |
|------|----|------|
| 결과 품질이 좋아지나? | **아직 단정할 수 없다.** 의도 파악에서는 개선 신호가 있다 | 표본이 1~2회뿐이고 평가자(grader)도 불안정해서, 저자들도 "효과를 결론 낼 수 없다"고 적었다 |
| 시간·비용은? | **확실히 늘어난다.** 코드 리뷰 1건 기준 시간 6.3배, 작업 에이전트 비용 13.9배 | 공식 평가 레포의 순정(stock) vs superpowers 실험 |
| 고정 비용은? | 세션마다 약 490단어, brainstorming이 발동되면 1,724단어가 컨텍스트에 추가된다 | 스킬 파일 단어 수 (토큰으로는 대략 0.6k / 2.3k) |

정리하면 **"품질 향상은 그럴듯하지만 아직 증명되지 않았고, 비용 증가는 분명하다."**
그래서 v7.0.0은 첫 점검(요청에 다 있으면 바로 실행)과 옵트아웃(질문 건너뛰기)으로 **필요 없는 경우의 비용을 줄이는 쪽**으로 설계됐다.

## 데이터 출처

superpowers 팀은 별도 평가 레포 [prime-radiant-inc/superpowers-evals](https://github.com/prime-radiant-inc/superpowers-evals)에서 스킬의 행동을 측정한다.

- **방식:** 실제 Claude Code·Codex CLI를 컨테이너 안에서 띄운다. **시뮬레이션 사용자**(LLM)가 대화를 진행하고, 끝나면 **평가자**(LLM, Sonnet 5)가 시나리오별 기준으로 채점한다. 결정적 검사(테스트, grep 같은 post-check)도 함께 돌린다.
- **비교 단위(arm):** `superpowers: none`인 **stock**(순정)과 superpowers를 특정 커밋으로 고정한 **treatment**를 같은 모델·같은 작업으로 돌린다.
- 이 문서의 수치는 모두 그 레포의 `docs/experiments/` 기록(2026-09)에서 가져왔다. treatment는 **superpowers v6.3.0**(`b36e082`)이다.

> ⚠️ **v7.0.0 측정치는 아직 없다.** 평가 레포의 마지막 커밋(2026-09-11)이 v7 출시(2026-10-09)보다 이르다. 아래 수치는 이전 brainstorming(3분기 라우터 버전) 기준이다.

## 결과 1 — 일상 작업 비교 (순정 vs superpowers)

출처: `2026-09-10-routine-use-native-doctor.md` · Claude Opus 5, effort high

계획은 36회(Claude·Codex × 설계, 코드 리뷰, 리뷰 피드백, 설정 수정 × 순정/superpowers × 2회)였다.
하지만 측정 인프라 결함으로 두 번 모두 중간에 취소됐고, **Claude 첫 반복분만** 완료됐다.

**코드 리뷰 1건**

| 지표 | 순정 | superpowers | 차이 |
|------|-----:|------------:|-----:|
| 기계 채점 | pass | pass | 같음 |
| 대화 시간 | 73초 | 461초 | **6.3배** |
| 작업 에이전트 비용 | $0.33 | $4.63 | **13.9배** |
| 평가 역할(시뮬레이션 사용자+평가자) 비용 | $0.20 | $6.39 | 32배 |
| 하위 세션 / 모델 호출 | — | 하위 세션 19개, 모델 호출 232회 | |

- 운영자가 직접 다시 확인해 보니 **양쪽 다 근거를 과장한 주장이 1건씩** 있었다.
  순정은 SQL 인젝션 우회 방식을, superpowers는 "비밀번호 평문 저장"을 증거 이상으로 단정했다. 둘 다 기계 채점은 pass였지만 실제 리뷰 품질 차이는 드러나지 않았다.
- 비용이 커진 이유는 brainstorming 때문이라기보다 superpowers 전체 워크플로(서브에이전트로 작업 나누기, 리뷰 스킬 등) 때문이다. 코드 리뷰는 brainstorming이 주로 쓰이는 작업이 아니다.

**설정 수정 1건:** 양쪽 모두 pass. 둘 다 재현 → 수정 → 검증 순서를 지켰다.

**설계 1건 (brainstorming이 직접 관여하는 작업)**

| | 순정 | superpowers |
|--|------|-------------|
| 기계 채점 | pass (10개 기준 모두 운영자도 동의) | **채점 불가** — 평가자 요청이 시간 초과 |
| 운영자 수동 감사 | — | 10개 기준 중 9개 충족, 1개 미충족("로컬 브라우저 전용인지" 확인 누락) |

→ brainstorming이 설계 대화에서 순정보다 낫다는 증거는 이번 표본에서 **나오지 않았다.** 순정도 필요한 질문을 다 했다.

## 결과 2 — 코드 리뷰 스모크 (n=2)

출처: `2026-09-10-conversation-code-review-smoke.md`

Claude·Codex·Pi × 순정/superpowers × 2회 = 12회. 12회 모두 끝까지 실행됐지만 **평가자 쪽이 실패**했다.
평가 12건 중 4건은 평가자가 보고서 형식을 계속 틀려 시간 초과로 "판정 불가"가 됐다(Claude superpowers 2회 모두 포함).
저자들도 이 실행으로 **"순정 대비 효과"를 답할 수 없다**고 명시했다.

> 배울 점: LLM 에이전트를 LLM으로 평가할 때는 **평가자의 신뢰도부터 검증**해야 한다. 그렇지 않으면 측정하려는 차이보다 측정 도구의 오차가 더 크다.

## 결과 3 — brainstorming 개선 PR 전/후

출처: `2026-09-06-pr2258-five-model-campaign.md` · superpowers PR #2258 "fix: preserve shared intent through design and planning"

순정 비교가 아니라 **brainstorming 이전 버전(base) vs 개선 버전(head)** 비교다. 5개 모델, effort xhigh, 9개 행동 시나리오.

| arm | n | 통과 / 실패 / 판정 불가 | 작업 에이전트 비용 |
|-----|--:|------------------------|-------------------:|
| Claude Opus 5 base | 8 | 4 / 3 / 1 | $13.46 |
| Claude Opus 5 head | 8 | **6 / 1 / 1** | $17.90 (+33%) |
| Claude Opus 4.8 base | 6 | 2 / 0 / 4 | $5.30 |
| Claude Opus 4.8 head | 5 | 4 / 0 / 1 | $5.98 |
| Codex Sol base → head | 9 | 7/0/2 → 7/0/2 | $8.36 → $8.74 |

**의도 파악 시나리오**(`brainstorming-todo-purpose-discovery`, 투두 앱을 만들어 달라는 요청에서 "왜 필요한지"를 끌어내는지 측정):
- Opus 5: base **실패** → head **통과**. base는 학습 목적을 끝까지 묻지 않았고 head는 물었다.
- Astra·Sol·Opus 4.8은 base부터 통과, Luna(가장 싼 모델)는 둘 다 실패.

→ 프롬프트를 의도 파악 쪽으로 다듬으면 **일부 모델에서 효과가 보인다.** 다만 n=1이고, 모델이 약하면 프롬프트로도 못 메운다(Luna).
v7.0.0 재작성은 이 방향을 더 밀어붙인 버전이다.

## 왜 비용이 늘어나나

1. **고정 컨텍스트:** 세션 시작 훅이 `using-superpowers`(약 490단어)를 매번 넣고, brainstorming이 발동되면 1,724단어 스킬을 읽는다.
2. **대화 턴 증가:** 질문 1개씩, 플레이백 200~300단어씩. 사람 입장에서는 왕복 횟수가 늘어난다.
3. **서브에이전트:** Builder check, 그리고 이후 subagent-driven-development에서 작업마다 새 에이전트를 띄운다. 코드 리뷰 실험의 하위 세션 19개가 이 경우다.
4. **문서 산출물:** 설계 문서 → 구현 계획 → 실행. 단계마다 쓰고 읽는 토큰이 든다.

## 언제 쓰면 이득이고, 언제 손해인가

| 상황 | 판단 | 이유 |
|------|------|------|
| 요구사항이 모호한 새 기능·새 프로젝트 | **이득** | 잘못 만든 뒤 되돌리는 비용이 질문 몇 번보다 훨씬 크다 |
| 플랫폼·언어를 사람이 정해야 하는 일 | **이득** | iOS 앱 요청에 웹 앱을 만든 사고(#2482)가 실제로 있었다 |
| 여러 사람이 볼 설계 문서가 필요할 때 | **이득** | Builder check로 빈칸이 줄어든 문서가 남는다 |
| 명확한 한 줄 수정, 오타, 설정값 변경 | 손해 → v7에서 완화 | 첫 점검에서 바로 실행으로 빠지게 설계됐다 |
| 빠르게 시험해 보는 프로토타이핑 | 손해 → v7에서 완화 | 옵트아웃 또는 스파이크로 게이트를 건너뛸 수 있다 |
| 토큰 비용에 민감한 자동화 파이프라인 | **손해** | 고정 컨텍스트와 서브에이전트 비용이 누적된다 |

## 한계

- 모든 수치가 **n=1~2**이고, 대부분 인프라 결함으로 캠페인이 중간에 끊긴 상태에서 나온 부분 결과다.
- 평가자(LLM) 판정을 운영자가 다시 보니 뒤집히는 경우가 있었다(근거 과장을 pass로 준 사례들).
- 측정 대상은 v6.3.0이다. v7.0.0의 첫 점검·옵트아웃이 비용 증가를 얼마나 줄였는지는 측정된 적이 없다.

## 직접 측정해 보려면

같은 요청을 superpowers 설치/미설치 상태의 Claude Code에 각각 여러 번 주고 비교하면 된다.

| 측정 항목 | 방법 |
|-----------|------|
| 시간·토큰·비용 | `claude -p --output-format json` 결과의 `duration_ms`, `usage`, `total_cost_usd` |
| 대화 턴 수 | 사람 역할을 정해진 답변 스크립트(또는 시뮬레이션 사용자)로 고정 |
| 의도를 물었는가 | 첫 응답이 바로 코드인지, 목적·사용자·제약을 묻는지 |
| 결과가 맞았는가 | 숨겨 둔 요구사항(예: "모바일에서 써야 함")을 반영했는지 체크리스트로 채점 |

요청 예시: 명확한 작업 1개("버튼 색 바꾸기"), 모호한 작업 1개("팀용 투두 앱"), 숨은 제약이 있는 작업 1개. 작업마다 5회 이상 돌려 평균과 분산을 함께 본다.
